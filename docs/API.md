# HTTP API

Base URL: `http://127.0.0.1:8000`. The browser UI is served from the same origin. [OpenAPI 3.1](openapi.json) and [JSON schemas](../schemas/) are generated by `scripts/generate_artifacts.py`. Input schemas describe wire shape; runtime validation additionally enforces references, scope, chronology, assumptions and immutability.

Except `/healthz` and the three static UI files, requests require `Authorization: Bearer TOKEN`. POST bodies use `Content-Type: application/json` and one Content-Length header, at most 16 MiB. No CORS, URL-based acquisition, arbitrary filesystem paths, chunked uploads or executable transforms are exposed. A hostile Host or cross-origin Origin is rejected. Rate capacity is 16 concurrent HTTP requests and two analyses per server process.

| Access | Endpoints |
|---|---|
| Public | `GET /healthz` (liveness only), `/`, `/app.js`, `/style.css` |
| Reader, analyst, reviewer, release | `GET /v1/health`, `/identity`, `/adapters`, `/examples`, `/graphs`, `/schemas`, `/search?q=...`, `/objects?kind=...&limit=100&offset=0` |
| Same read roles | `GET /v1/sources/{id}`, `/evidence/{id}`, `/claims/{id}`, `/models/{id}`, `/protocols/{id}`, `/runs/{id}`, `/releases/{id}` |
| Same read roles | `GET /v1/claims/{id}/proof`, `/proofs/{id}` (ZIP bytes) |
| Analyst | `POST /v1/import`, `/demos`, `/sources`, `/evidence`, `/claims`, `/models`, `/protocols`, `/objects`, `/verify` |
| Analyst | `POST /v1/protocols/{id}/freeze`, `/runs`, `/runs/{id}/proof` |
| Reviewer | `POST /v1/reviews/{id}` |
| Release | `POST /v1/releases` (requires a configured release key) |
| Reviewer or release | `GET /v1/audit` |

`admin` permits all actions. The default generated credentials are separated analyst/reviewer/reviewer2/release identities, without an admin token. Authorization is workspace-wide, not per-row or multi-tenant.

## Example API lifecycle

Set `FCEA_TOKEN` privately in your shell to the generated analyst token. Do not put credentials in committed files or public command logs.

```sh
curl -s http://127.0.0.1:8000/v1/demos \
  -H "Authorization: Bearer $FCEA_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"policy-rct"}'
curl -s http://127.0.0.1:8000/v1/protocols/policy_rct.protocol/freeze \
  -H "Authorization: Bearer $FCEA_TOKEN" -H 'Content-Type: application/json' -d '{}'
curl -s http://127.0.0.1:8000/v1/runs \
  -H "Authorization: Bearer $FCEA_TOKEN" -H 'Content-Type: application/json' \
  -d '{"protocol_ref":"policy_rct.protocol"}'
```

Use the returned run `id` with `POST /v1/runs/{id}/proof` and `{ "public": false }`. Use the returned packet `id` to download `GET /v1/proofs/{id}` with the same Authorization header. Marking a packet public applies redistribution checks; it does not publish it to an external website or disable authentication.

`POST /v1/sources` takes `{ "metadata": {...}, "content_base64": "..." }`. Required acquisition metadata: `id`, `origin`, `known_at`, `legal_basis`, `media_type`; the service supplies `sha256` and `acquired_at`. Optional flags and parent/dependency references are described by `SourceSpec`. `POST /v1/evidence` takes `EvidenceItem` extraction fields; the service calculates `value` or checks that the supplied value exactly matches extraction. `POST /v1/objects` accepts `{ "kind": "ScopeSpec", "payload": {...} }` and only registered input types.

Import uses complete bundles as in `examples/`. An object with identical ID/content is idempotent; the same ID with different contents returns a conflict. Import may leave preceding valid objects if a later object fails; retry with a corrected bundle. Parameters cannot be overridden on the run endpoint.

Review body: `{ "action": "APPROVE", "reason": "Evidence and limitations reviewed", "conflict_of_interest": false }`. Target is the exact run or contradiction EvidenceLink, not a mutable latest alias. Release body: `{ "run_ref": "run-...", "public": false }`. Reviews and releases do not mutate machine verdicts.

HTTP 200 means the operation returned successfully; inspect scientific/execution/validity states. Error codes: 401 missing auth; 403 invalid auth/role/Host/Origin; 404 unknown object/route; 409 immutable conflict or run capacity; 422 validation/integrity failure; 408 timeout; 500 unexpected server failure; 503 exhausted HTTP capacity. Errors contain an `error` message, usually a `code`. They never fabricate successful results.
